# 最小等待程序与双侧追踪结果

2026-10-18，Windows + WSL2 / Ubuntu 22.04。**已完成本轮隔离诊断，尚未获得可稳定消除尾部间隙的策略，B4/B5仍未通过。** 没有开展模式、联合分布拟合或可靠度预测。

最直接的结论：**不运行ORB-SLAM3，同类超过100微秒的启动间隙仍可出现。** 这说明SLAM的跟踪/建图不是该现象出现的必要条件；不能由此断言此前每一个SLAM异常都具有同一个原因。

协议见[参数与复现](wait-isolation-protocol-2026-10-18.md)、[主参数](wait-isolation-protocol-2026-10-18.json)、[中断补查](wait-isolation-irq-vectors-2026-10-18.json)及[宿主流式补查](wait-isolation-host-stream-2026-10-18.json)；完整数值、源文件/二进制哈希和核验见[JSON](wait-isolation-results-2026-10-18.json)。本轮有效数据包括12次无诊断基准、6次有效主追踪和4次专项补查，另保留6次PID过滤错误的采集。

## 1. 不含SLAM的基准

同一独立C++二进制，不导入ORB、OpenCV或Eigen。每次800轮、50 ms周期；无额外诊断、无绑核、无实时优先级、无专门伴随负载，Windows正常后台环境保持。模拟计算持续约20 ms墙钟，并非固定20 ms CPU工作。12次均完成，全部9600轮时间戳与执行先后检查通过。

| 工作 | 等待 | 三次最大启动间隙 / µs | 超100 µs轮次 / 2400 | 三次CPU时间/墙钟 |
|---|---|---|---|---|
| 无计算 | 普通休眠 | 413.891 / 249.176 / 411.560 | 2276/2400 | 0.05% / 0.05% / 0.05% |
| 无计算 | 500 µs主动检查 | 129.850 / 20.861 / 78.955 | 1/2400 | 0.81% / 0.80% / 0.81% |
| 20 ms模拟计算 | 普通休眠 | 363.561 / 438.624 / 334.773 | 2278/2400 | 39.99% / 39.99% / 40.00% |
| 20 ms模拟计算 | 500 µs主动检查 | 190.342 / 200.028 / 160.030 | 6/2400 | 40.74% / 40.75% / 40.74% |

启动间隙定义为 `start-max(release,previous_end)`，不是累计窗口模型误差。这些轮次数不能与原SLAM的H=20窗口数混算。100 µs仍是模型对应的误差门槛，任务截止仍为50 ms，没有把二者混淆或调整。

主动检查改善普通休眠的迟到，但未给出稳定小于100 µs的保证。无计算时两次没有超限，不能用其替代含计算时三次超限的结果，更不能从有限样本得到操作系统调度上界。

每次有效记录均捕获休眠、唤醒和切换正对照；保存的各CPU overrun、commit overrun、dropped events计数用于独立检查。初版发行版PID过滤导致空追踪，已识别为采集错误：例如短测本地PID 60对应内核PID 451。最终入口由子进程自己写trace_marker建立映射；初版六次原始资料保留并排除，不将空追踪当成“没有切换”。

常规irq_handler事件不覆盖本地APIC定时器等向量中断，所以又事前冻结两次补查，加入local_timer、reschedule、call_function、irq_work等入口/出口。补查不启用宿主WPR，不与主追踪合并解释为性能重复。

主追踪中，超100 µs的读钟间隔共有21轮，其中0轮与已配对的来宾切换/中断区间重合；向量补查对应为10轮与0轮。重合仅是定位线索，不能把整个间隙都计为该事件的耗时。事件文本精度为微秒，匹配保留±1 µs边界。

补查中没有实际捕获到这些APIC向量事件，因而没有建立向量中断的正对照。不能把“事件已启用”提升为“排除了所有中断”；WSL/Hyper-V可能还有本批事件未覆盖的路径。本批已核验的调度与软中断事件也未解释全部长间隙。

具体例子：向量补查的20 ms计算条件中，k=298相邻读钟间隔为134.085 µs，最终启动间隙118.454 µs；对应区间没有捕获到切换或已启用的中断事件，线程CPU编号保持19，非自愿切换计数也未增加。k=362的读钟间隔更大，为213.353 µs，但因更早开始主动检查，最终启动间隙只有51.292 µs。因此“出现长读钟间隔”和“实际启动超100 µs”也必须分别统计。

## 3. 宿主证据能说明到哪里

六次主追踪使用64 MiB内存环形缓冲，启用ProcessThread、CSwitch、ReadyThread。xperf实际时间范围显示仅保留末尾4.97–5.70秒，尽管lost events/lost buffers都是0。它们是局部记录，不能称为完整对应证据。

因此另行冻结两次文件模式补查，同一探针、同样800轮，含来宾向量事件；临时/最终文件均写D盘任务目录，设置2 GiB文件量停止门槛。两份宿主记录实际事件跨度为40.578 / 41.629秒，均未报告丢失事件或缓冲；已核查事件类别和进程摘要。未触发空间停止门槛，具体峰值见JSON。原环形记录全部保留并标明不完整，不与流式记录混为同一采集。

这些记录证明本机可以继续取得宿主证据，尚不足以定位某个百微秒间隙的宿主原因：本轮未建立小于100 µs误差的来宾mono—宿主QPC时钟对应，也未把来宾CPU映射到Hyper-V虚拟处理器执行轨迹。Windows普通线程CSwitch不等于虚拟处理器调度；不能看到Vmmem就把其进程CPU摘要归因到某一帧。

MONOTONIC与MONOTONIC_RAW以及来宾线程CPU的端点也不完全相同，且并非完全独立的硬件证据。当前clocksource为tsc；两个时钟同时增长不能排除共同的虚拟化/计时停顿，线程CPU记账也不能独自证明期间持续执行了用户指令。

## 4. 对改造方案与下一步的影响

本轮没有发现足以支持再改Tracking/LocalMapping或扩大主动检查预算的直接证据。没有添加新调度策略、改变原生默认、修改数学图、把未建模等待塞入服务时间或放宽门槛。指定非惯性双目范围内B2/B3的既有结论保留；B4/B5仍由此前真实回放的失败证据约束，B6完整实用性及概率阶段没有推进为通过。

后续从平台间隙继续，而非重新改建图算法：

1. 若继续在WSL定位，先建立经过误差检验的主客时钟对应及Hyper-V虚拟处理器证据，再结合宿主DPC/ISR/调度检查异常；当前普通线程ETW不能替代这两项。

2. 只有识别出可控制原因，才设计可选、可配置且不影响原生入口的单因素对照。当前证据不支持把绑核、实时优先级、升级内核或加长忙等当作已经有效的修复。

3. 若WSL不能提供足够的处理器级证据或稳定性，另做原生Linux环境的最小程序对照，再决定是否迁移；不是立即要求新机器或重装当前系统，也不预设迁移必然成功。

4. 候选策略取得证据后，关闭新增诊断，用原50 ms周期/截止、H=20、100 µs门槛重跑真实SLAM及定位质量、资源、伴随任务条件。完整通过后才能继续模式、联合分布、可靠度评估。
