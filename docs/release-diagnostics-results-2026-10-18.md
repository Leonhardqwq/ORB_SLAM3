# 释放时序与共用负载诊断结果

2026-10-18，Windows + WSL2 / Ubuntu 22.04。**本轮完成延迟位置诊断和有针对性的调用准备对照；没有取得所有运行满足 100 微秒模型对应门槛的证据，B4/B5 仍未完成验收。** 概率拟合和可靠度预测未开始。

事前参数见[诊断协议](release-diagnostics-protocol-2026-10-18.md)及[参数](release-diagnostics-protocol-2026-10-18.json)，完整数值、命令关联和哈希见[结果 JSON](release-diagnostics-results-2026-10-18.json)。[上一批结果](fixed-usability-results-2026-10-17.md)保持原样，不用本轮重新解释其通过/失败。

## 完成范围

完成三档短回放、18 次时间戳回放、18 次前后独立伴随任务基准、3 次线程计数回放，以及另行冻结的 6 次调用准备开关对照。每次完整回放评估 800 帧。运行串行；不同插桩强度和候选布局分开分析。新增插桩与准备策略默认关闭，仅作用于独立回放应用。

保留 20 Hz、50 ms 截止、H=20、100 µs 累计模型对应误差、500 µs 主动检查预算、原服务时长与图；不绑核、不设实时优先级、不增加模型假设。100 µs 是模型对应误差，不能误读成任务的 100 µs 截止。实际截止等号仍算成功。

普通休眠六次共 240/240 个窗口超限；主动检查六次共 5/240 个窗口超限、2/6 次运行完全通过。后者仍明显改善模型对应，但没有稳定解决尾部间隙。以上是本批插桩条件下的结果，不与旧批次通过比例合并成统计可靠度。

- 普通休眠的 `idle-1-fixed_sleep`、k=193：截至休眠返回后的首次读钟已迟到 272.730 µs；随后两个分量为 0.510、6.514 µs，启动间隙共 279.754 µs。延迟主要已经出现在第一个返回时间戳之前；不能进一步仅凭该值区分内核睡眠结束、获得CPU和返回后取时间戳的细节。
- 主动检查的 `idle-2-fixed_hybrid`、k=466：提前 386.902 µs 醒来，主动检查退出只晚 0.005 µs，退出后到调用却用了 104.936 µs，其中探针后调用准备区间为 104.897 µs。这是移动记录准备操作的直接动机，但不证明记录初始化本身计算了 104.897 µs；该区间还可能被打断。
- `opencv_companion-2-fixed_hybrid`、k=748：提前 364.536 µs 醒来，主动检查内相邻读钟出现 152.199 µs 间隔，最后退出晚了 129.618 µs，后续 4.251 µs，启动共 133.869 µs。这里已经提前醒来，延长主动检查预算不能直接消除这类间隙。

全部逐帧启动间隙按等待前、休眠返回、主动检查、检查后调用四项精确相加；无负间隙裁剪，无探针开销扣除。窗口误差由原论文 `Model.step` 重新计算，未拿单帧间隙代替窗口验收。

## 2. 是否已经证明是线程被抢占

没有。独立线程计数批次三次最大模型误差为 176.944、88.108、145.860 µs，10/120 个窗口超限。2400 个主动检查测量区间的 Linux 非自愿切换增量均为 0。该档的 `idle-3-fixed_hybrid`、k=504 仍有 154.797 µs 的相邻读钟间隔。

这排除了“本批探针已经捕获Linux非自愿切换”这一说法，没有排除宿主/虚拟机调度、中断、读钟路径或其他停顿，也没有测到检查结束后整个调用准备区间的切换。线程 CPU 读数的区间与墙钟端点略不同，不能把两者相减直接当作精确抢占时长。当前 WSL 未安装 perf，`/sys/kernel/tracing/events/sched` 不可用；没有为取证修改系统权限或安装新内核。插桩本身增加了开销，该批结果不替代关闭诊断后的验收。

## 5. 当前判断与下一步

已确认的瓶颈是释放后的调度/观测间隙，而非已发现的跟踪—建图依赖错误。普通休眠主要在首次返回时间戳前迟到；主动检查的残余异常同时存在于循环内和调用前。尚不能把异常归结为某一种具体OS机制。

下一步宜先做同平台的最小等待程序对照，检查不运行SLAM时是否仍出现相同读钟间隙；随后对异常区间获取宿主/来宾的对应调度证据。若要测试处理器分配或平台专用调度，应另行冻结可选策略及共用任务代价，不把它们设为原生默认。继续保留当前图和服务定义，不把间隙藏入服务时长、不放宽100微秒门槛。诊断和候选优化都需要关闭新增探针后的独立工程验收，才能重新评估B4/B5；此时仍不能开始概率拟合。
